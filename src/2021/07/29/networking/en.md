---
title: "Misconceptions About Secure Networking"
date: 2021-07-29 21:19:00 +0800
---

There are many good people in the world, but there are bad ones too. The internet is no exception, so secure networking is needed everywhere. In mainland China, for reasons that are hard to state directly, this demand is especially strong.

Many approaches exist, and new ones keep appearing.

The earliest and easiest-to-find method was HTTP proxies, with many free servers available online. Before HTTPS was widely adopted, this basically sold all your information to the proxy server, and traffic between you and the proxy was plaintext. Even today, HTTP proxies still expose requested domains. Plain SOCKS proxies have similar issues.

About nine years ago, Shadowsocks started the era of encrypted proxies. It was very successful at first, but due to issues with cipher usage, it became easier to detect. Even without obvious handshake signatures, Shadowsocks traffic could still look suspicious (like a van with blacked-out windows), making it easier to block. So many obfuscation variants appeared. V2Ray similarly addressed many Shadowsocks limitations and added power, but configuration became overly complex. In recent years Trojan emerged, disguising traffic directly with TLS, but configuration complexity remained a problem.

On the VPN side, many solutions exist. PPTP used to be common but is now rare due to security issues. L2TP/PSK-IPSec still exists widely, but IPSec handshakes are fragile and often blocked, so reliability is limited. WireGuard won many people with clean design and great performance, but like other VPNs, it suffers from UDP constraints in China's network environment; and WireGuard has recognizable packet characteristics. There are TLS-based VPN options too, such as Microsoft's SSTP, but deployment is harder (native setup often requires Windows Server), open-source implementations are fewer (SoftEther is one), and hiding VPN intent on exposed ports is difficult.

To hide proxy/VPN intent and avoid ISP QoS targeting, both paths eventually converge on TLS camouflage as normal website traffic. But implementations are still not ideal, so recently I built many tools myself. I found these tools are not that hard to write, and many existing projects are too large and over-engineered. Core logic does not require that much code.

At first we used ordinary HTTP proxies, but client-to-proxy links can also be wrapped in TLS to hide proxy usage. So I wrote [go-shp](https://github.com/winguse/go-shp). Server-side alternatives existed (for example Caddy 1.x), but client support was limited at OS level; I only saw clear browser support in Chrome (maybe Firefox too), so I also wrote a local forwarding proxy. Since Chrome supported it, I even wrote a browser extension, though I bit off too much implementing auto-detection and auto-proxying.

However, HTTP proxies cannot forward non-TCP traffic by nature. For those needs I used WireGuard. Native WireGuard was too easy to identify, so I wrote [udp-xor](https://github.com/winguse/udp-xor). But plain XOR still has fingerprints, so while practicing Rust I wrote [udp-prepend](https://github.com/winguse/udp-prepend). UDP is good, but QoS is painful, so I wrote [ws-udp](https://github.com/winguse/ws-udp) to encapsulate UDP into WebSocket, which also enables TLS camouflage. This introduces TCP-over-TCP problems, but practical alternatives are limited. WireGuard already encrypts traffic, and adding TLS WebSocket felt redundant, which made me miss SSTP. But as mentioned, there was no implementation I really liked, so I wrote [ws-tun](https://github.com/winguse/ws-tun).

I once considered implementing an SSTP server, but the protocol is somewhat complex and harder to blend with normal traffic. So I chose to build a TUN/TAP VPN directly. Honestly I had found open-source websocket-based implementations, but one used a niche language and another lacked TLS, and both felt overcomplicated. Between TUN and TAP, I felt TAP was unnecessary and needs root privileges, so I chose TUN. Using WebSocket for TUN packet transport was natural. WebSocket overhead is acceptable, and I did not need to implement my own fragmentation logic. For TUN calls, I reused ideas from Cloudflare's boring-tun and adapted them. The hardest part was Rust development itself: compiling successfully was painful, and async refactoring cost a lot of time. The project runs well on macOS and Linux in practice. Configuration is also simple: client and server only need to agree on one WebSocket URL. I put both client and server into one binary, which is not ideal: server side is designed to sit behind nginx (so TLS config is unnecessary there), but this still increases binary size; client side must include TLS dependencies anyway.

Mobile support for ws-tun was harder because I had not written mobile apps before. This week I spent some time and built [ws-tun-android](https://github.com/winguse/ws-tun-android). Android VPN development turned out to be straightforward—Google's ToyVPN sample helped a lot. But when I tried iOS last night, things were not easy: a developer account is mandatory, and NetworkExtension seemed restricted to enterprise use? So I gave up for now.

Anyway, maybe after some time I will no longer need to keep tinkering with this. Let this post be a summary of my many years of networking experiments: from using others' services, to assembling services from others' code, and finally writing my own implementations from scratch. Thanks, GFW—you taught me a lot.
